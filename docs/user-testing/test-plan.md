# แผนทดสอบผู้ใช้จริง V4 (#151)

## เป้าหมาย

สังเกตว่าผู้ใช้จริงทำงาน TC1 และ TC2 ได้จากเป้าหมายที่อ่านให้ฟัง โดยไม่มีผู้ทดสอบบอกขั้นตอนหรือชี้ชื่อปุ่ม เก็บผลสำเร็จ เวลา ความช่วยเหลือ จุดติดขัด และความเห็นหลังทำงาน เพื่อใช้ยืนยันพฤติกรรมจริงของ #146 และ #147

### Readiness gate

- [ ] #145 (การนำทาง) พร้อมใช้งานบนสภาพแวดล้อมทดสอบ เพื่อให้ TC1 และ TC2 ไปถึงผลลัพธ์การนำทางจริงได้
- [ ] #146 และ #147 merge และ deploy แล้ว หรือ tech lead ระบุ build ที่ทดสอบได้โดยชัดเจน
- [ ] ใช้ personal AWS Academy `dev` test stack ที่แยกจาก production และผู้ทดสอบคนอื่น มีข้อมูลทดสอบที่รีเซ็ตได้ (ยืนยันตาม [test-fixtures.md](./test-fixtures.md))
- [ ] กรอก [test-fixtures.md](./test-fixtures.md) ให้ครบและตรวจยืนยัน target dev stack ก่อนสร้างบัญชี/ข้อมูล
- [ ] ยืนยัน fixture ทางเดินและ physical alternative route ด้วย build ที่ deploy จริง; ห้ามเริ่มถ้ายังใช้ candidate edge ที่ไม่ผ่านการตรวจ
- [ ] TC1 มีรายการสอบ BAS350 เวลา 13:00–16:00 ในวันที่ทดสอบ หรือมีวิธีค้นหารายการที่ผ่านไปแล้วตาม UI จริง โดยผู้ทดสอบไม่เห็นห้องก่อนเริ่ม
- [ ] TC2 มีรายการกิจกรรมทดสอบที่ย้ายห้องได้ และมีทางเดินที่ปิดแล้วทำให้เส้นทางนำทางเปลี่ยนจริง
- [ ] ทดสอบเส้นทางก่อน/หลังปิดและตรวจว่าห้องต้นทาง/ปลายทางยังเข้าถึงได้ ไม่ทำให้ผู้ใช้ไปถึงทางตัน
- [ ] ระบุ source location, เวลา, วัน, ห้องปลายทาง และช่วงทางเดินที่ปิดใน fixture sheet ของผู้ดำเนินการ โดยไม่เปิดเผยคำตอบให้ผู้เข้าร่วมก่อนงาน
- [ ] มีผู้เข้าร่วมอย่างน้อย 3 คนจากอย่างน้อย 2 role พร้อมเวลานัดยืนยัน (ดูตารางผู้ทดสอบ)
- [ ] มีบัญชีทดสอบตาม role, อุปกรณ์, ผู้ดำเนินการ และผู้สังเกตการณ์พร้อม
- [ ] สำรองค่าเดิมและทำ checklist ใน [reset-checklist.md](./reset-checklist.md) เสร็จ

**ข้อจำกัดของข้อมูลสอบ:** seed [lc3-schedules.seed.json](../../tools/data-extraction/lc3/lc3-schedules.seed.json) มีรายการสอบ BAS350 เวลา 13:00–16:00 ห้อง LC3-103 วันที่ 2026-05-18 ซึ่งผ่านไปแล้วก่อนวันทดสอบ 29–30 ต.ค. อย่าแก้ไฟล์ seed ที่สร้างอัตโนมัติหรือใช้ production เพื่อเตรียม test fixture ให้สร้างข้อมูลทดสอบใน personal dev test stack ตาม [test-fixtures.md](./test-fixtures.md) เท่านั้น และตรวจว่าผู้ใช้ค้นพบได้ก่อนเริ่มงาน

## ผู้เข้าร่วมและนัดหมาย

ต้องมีอย่างน้อย 3 คน โดยมีอย่างน้อย 2 role; แนะนำให้มีผู้ใช้/นักศึกษาอย่างน้อย 2 คน และ staff อย่างน้อย 1 คน เพื่อทดสอบทั้ง TC1, TC2 staff และ TC2 participant ผู้เข้าร่วมหนึ่งคนทำได้มากกว่าหนึ่ง task แต่ต้องบันทึกผลแยก task

| 1 | รอผู้จัดยืนยัน | รอยืนยัน | รอยืนยัน | ไม่ |
| 2 | รอผู้จัดยืนยัน | รอยืนยัน | รอยืนยัน | ไม่ |

บันทึกชื่อในเอกสารที่อยู่ใน repo เฉพาะเมื่อผู้เข้าร่วมอนุญาตและ repo/เอกสารเหมาะกับการเปิดเผย หากไม่เหมาะ ให้ใช้รหัสผู้เข้าร่วมใน repo และเก็บรายชื่อจริงนอก repo อย่างปลอดภัย การแทนที่ด้วยรหัสไม่ใช่การยืนยันนัดหมายแทนผู้จัด

## รูปแบบและลำดับการทดสอบ

- นัดหมายเป็นรายคน; จัดช่วงเวลาประมาณ 20–30 นาทีต่อคน รวมชี้แจง ยินยอม ทำ task และแบบประเมิน
- หนึ่ง TC2 cycle ประกอบด้วย staff ที่เปลี่ยนข้อมูลและผู้เข้าร่วมที่ค้นหาหลังเปลี่ยน; บันทึกทั้งคู่เป็น cycle เดียวและ reset ก่อน cycle ถัดไป
- ทำ TC1 และ TC2 participant ณ อาคาร LC3 เพื่อสังเกตการไปถึงห้องจริง; ให้ผู้เข้าร่วมทำงานบนอุปกรณ์ที่เลือกใช้จริง บันทึกชนิดอุปกรณ์/ขนาดหน้าจอและสภาพแวดล้อมใน [result-template.md](./result-template.md)
- กำหนดจุดเริ่มต้นในอาคารที่ปลอดภัยและใช้จุดเดียวกันสำหรับการเปรียบเทียบ route; ผู้สังเกตการณ์เดินตามในระยะที่ไม่ชี้นำและบันทึกการถึงห้อง/การเลี้ยวผิด
- closure เป็นข้อมูลจำลองในระบบเท่านั้น ห้ามกีดขวางทางเดินจริงหรือพาผู้เข้าร่วมเข้าเขตอันตราย; ตรวจว่าเส้นทางทางกายภาพที่ใช้ทดสอบเปิดและปลอดภัย
- ใช้ [scenario-cards.md](./scenario-cards.md) อ่านข้อความตามตัวอักษร ห้ามบอกวิธีใช้หรือชื่อ UI
- ลำดับที่แนะนำ: TC1 (ผู้ใช้) → TC2 (staff) → TC2 (ผู้เข้าร่วม) เพื่อให้ผู้เข้าร่วม TC2 พบข้อมูลหลัง staff ปรับแล้ว
- ห้าม reset ระหว่าง TC2 staff กับ TC2 participant; ทำ reset หลังผู้เข้าร่วม TC2 เสร็จเท่านั้น
- ใช้ [reset-checklist.md](./reset-checklist.md) หลังทุก cycle และให้ผู้ตรวจคนที่สองยืนยัน baseline ที่อ่านกลับจากระบบก่อนรับผู้เข้าร่วมคนถัดไป
- ผู้สังเกตการณ์บันทึกการกระทำและคำพูดตามจริง ไม่ช่วยเหลือ ยกเว้นตามเกณฑ์หยุดงานใน [observer-guide.md](./observer-guide.md)
- กรอกผลหนึ่งชุดต่อผู้เข้าร่วมต่อ task; บันทึกเวลาเริ่ม/จบแยก task
- ไม่ใช้ข้อมูลหรือบัญชี production และไม่บันทึกรหัสผ่าน, token หรือ secret ลง repo

## เกณฑ์ประเมิน

บันทึกผลแต่ละ task เป็น `สำเร็จด้วยตนเอง`, `สำเร็จแต่ได้รับความช่วยเหลือ`, `บางส่วน`, `ไม่สำเร็จ` หรือ `ยุติ` ห้ามรวมผลเหล่านี้เป็น PASS เดียวโดยไม่แสดงจำนวนและหลักฐาน

- **TC1:** ค้นพบรายการสอบที่ตรงกับ BAS350 และเวลา 13:00–16:00 ระบุห้องถูกต้อง ได้เส้นทางไปห้องนั้น และไปถึงห้องจริง
- **TC2 staff:** ย้ายกิจกรรมไปห้องเป้าหมายและตั้งการปิดทางเดินตามเวลา/เหตุผลที่โจทย์กำหนด โดยข้อมูลที่บันทึกมีผลจริง
- **TC2 participant:** ค้นพบห้องจัดกิจกรรมหลังย้าย และเส้นทางที่แสดงหลีกเลี่ยงทางเดินที่ปิด; ไปถึงห้องใหม่จริงโดยไม่ผ่านช่วงปิดในระบบ
- **ความช่วยเหลือ:** การบอกใบ้ทุกครั้งทำให้ task ไม่ใช่ “สำเร็จด้วยตนเอง”; บันทึกคำพูดและช่วงเวลาที่เกิด
- **เวลาทำ task:** จับจากอ่านโจทย์จบจนผู้ใช้ประกาศว่าจบ/ยืนยันจุดหมาย หยุดจับเมื่อขอหยุดหรือหมดเวลาที่กำหนด
- **ความถูกต้องของเส้นทาง:** ผู้ดำเนินการตรวจปลายทางและสถานะปิดกับ fixture ที่อนุมัติก่อน session ไม่ตัดสินจากคำกล่าวของผู้ทดสอบอย่างเดียว

รายงานสรุปต้องแสดงผู้เข้าร่วมทั้งหมดแยกตาม role, จำนวน task ต่อสถานะ, เวลาต่อ task, จำนวน/ชนิดความช่วยเหลือ, ปัญหาที่พบ และคะแนน/คำตอบหลัง task ห้ามเปิดเผยข้อมูลส่วนบุคคลเกินจำเป็น
